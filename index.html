Public write-up

How I ship ~9x faster with a multi-agent Claude workflow

I lead media generation benchmarking at Artificial Analysis. Over 19 months I went from ~13 handwritten PRs a month to 115 PRs built by agents in July 2026, and reverts fell from 5 in 2025 (plus 3 hotfixes) to 1 in the agent era. All numbers come from the git/GitHub history of one production monorepo (505 merged PRs, ~2,500 branch commits).

Written August 2026. Numbers current through Aug 7, 2026. Single self-contained file, no trackers, no external requests.

2 · Three Eras of Working

The velocity chart splits into three regimes, and the character of the work changes more than the count does.

2025 - Manual (157 PRs, ~13/month)

  • The work was scripts and provider wiring, with PR bodies so bare that 64% were empty and only 8 of 157 carried handwritten prose.
  • PRs came in big bangs, one landing +10k/-9.5k lines in 43 commits and another taking 211 commits to ship a 111-line change.
  • I shipped first and discovered problems later (one feature merged and reverted 3 days later, 5% of titles saying "temp/hotfix/rollback"), and the habit predated this system, as one Aug 2025 PR body shows in full: "made with cursor agent + gpt-5. Would be curious how cooked it is ;D"

Jan-May 2026 - Single-Agent Claude Code (141 PRs, ~35/month excluding a holiday month)

  • This was the template era, when 89% of PRs got a Summary + Test plan applied uniformly to the point of ritual (a PR adding one logo image got a full test plan).
  • Internal tooling jumped from 5% to 29% of PRs, and I spent the rest of the year living in the dashboards and trackers that era produced.
  • Work shifted from repair to design, with 2025's "temporary fix" PRs becoming engineered integrity features, though I still bundled too much into single PRs and one of them ran to 117 commits.

Jun 2026+ - Multi-Agent Orchestration (207 PRs, ~93/month)

  • The unit of work is now the program: stacks of 6 and 7 PRs with merge order encoded in the title ([PR n/N - Program Name]), and half of all PR bodies reference another PR (2% -> 9% -> 50% across the eras).
  • Bodies carry evidence: unchecked - [ ] boxes fell from 80% of PRs to 20%, displaced by actual run output (type-check/lint/test results, plus production EXPLAIN ANALYZE plans pasted into the body).
  • The review loop is visible in history: review bot findings and cross-vendor review batches are named and answered in PR bodies, and review fix commits went 2 -> 7 -> 24 per era.
  • Two models co-author one PR: 23 PRs carry the orchestrator and its implementing subagent as joint co-authors, and since June every commit also carries a session transcript link (0 before June, 495 after).
  • The system builds its own tooling: ~8% of PRs ship runbooks, CLIs, and agent skills for future agent runs, a category that didn't exist in earlier eras.

The Session Model

  • One long-lived session covers one vague context and many tasks. In that stretch one session ran a whole program area for five days (591 messages), another covered a single evening's page fix, and workstreams are born inside the session as things come up, each getting a thread letter the moment it spawns.

5 · The Architecture

The system has four layers. The leverage comes from writing all four down, so every session starts from the same contract instead of re-deriving it.

One frontier model (Claude Fable 5 today) runs the main loop and never writes non-trivial code. It verifies premises, writes briefs, spawns implementer subagents (currently Claude Opus tier) in isolated git worktrees, reviews their diffs like a human reviewer would, and owns every verdict. Independent review pressure comes from three directions: each implementer runs its own adversarial "bug bash" subagent before reporting, a second vendor model (OpenAI's Codex CLI in read-only mode) gives an advisory review of every diff, and the team's PR review bot comments on the open PR. The human (me) reviews on GitHub and owns the merge.

The Principles Under It

  1. Orchestration and typing are separate jobs. The main loop model's context window is the scarce resource, so bulk work (file sweeps, long threads, transcripts, implementation) happens in subagents that return distilled summaries.
  2. Premises are the safety boundary. Implementer agents execute flawed briefs without pushing back, so the orchestrator verifies every premise against the repo and memory before writing the brief and ends every brief with the line "If the repo contradicts this brief, stop and report instead of implementing."
  3. Review is structural and mandatory. Review runs in a fixed order (nested bug bash -> cross-vendor advisory review -> recursive loop until a round produces zero findings worth fixing -> PR bot triage with a reply on every thread), and at least two readers see every diff before it reaches a PR.
  4. Parallelism has no artificial cap. N independent units of work get N subagents (one per file to migrate, model to probe, PR to triage), coordinators recurse bounded at depth 5, and each level returns only distilled findings upward.
  5. Everything learned gets written down. Corrections, gotchas, and workflow improvements land in persistent memory files or skill documents, and a retro agent reads the full session transcripts at the end of each workstream and proposes edits to the system itself.

6 · Layer 1 - The CLAUDE.md Contract

A global ~/.claude/CLAUDE.md loads into every session. Mine has two halves: a communication contract (how answers must be formatted so I can process dozens of agent reports a day) and the delegation policy (section 7). The communication half, distilled:

  • Answer format.
    • Numbering. Every substantive answer is a numbered hierarchy (1 -> 1.1 -> sub-bullets), one idea per point, so I can reference any finding by number ("apply 2.3, skip 2.4"), with each point one full sentence rather than a run of clipped fragments.
    • Thread letters. Each workstream gets a stable letter for the session, every message opens by naming its thread with both the letter and the name, and a message spanning threads splits into sections, because I run one long-lived session per broad context and interleaved agent reports become unreadable without this rule.
    • Numbered phases and PRs. Phases and PRs take numbers (letters stay reserved for threads), and stacked PRs are numbered in merge order, in the GitHub title itself ([PR 2/6 - Program Name] ...), so the PR list reads as a merge plan without opening anything.
  • Verdicts and evidence.
    • Binary verdicts. Investigations end in a green/red call at the top, with caveats underneath as notes, the deep work done before the short answer goes out, and ambiguity triggering more research rounds instead of a yellow verdict.
    • Signal density. Every number, path, and stated uncertainty survives editing, only the surrounding prose goes, and when a paragraph and a table carry the same values the table wins.
  • Language and interaction protocol.
    • Simplified Technical English. Procedures and docs use one name for one thing, active voice, short common words, and one instruction per sentence, with every condition coming before its command.
    • Answers before implementation. A message phrased as a question gets a grounded answer and recommendation while implementation waits for an explicit go, and a remark that merely sounds like a principle ("we should never X") earns one short clarifying question first, because it may be me thinking out loud rather than a spec.
    • Chat references only. The plan/code file is canonical and chat gets references to the diff, because I review diffs on GitHub where uncommitted local edits are invisible to me, and "check the file" is not a handoff.

At 30+ PRs a week from agents, my reading speed is the limit, and the contract is what makes an agent report triageable in seconds. The "answers before implementation" rule earned its place after an agent turned an offhand remark of mine into an enforced rule in production code that I had to back out.

7 · Layer 2 - The Delegation Policy

Division of Labor

  • The orchestrator (frontier tier) never implements non-trivial changes. It verifies premises, writes briefs, reviews diffs, and owns verdicts, implementing directly only for trivial edits (<~5 lines) where the delegation round-trip costs more than it saves, or after a delegated attempt failed review twice.
  • Implementers (strong but cheaper tier) do all exploration and code writing. Each one is a fresh agent with edit access working in an isolated git worktree, every spawn names its model explicitly (a spawn without a model parameter is a policy violation even for "cheap" read-only searches), and coordinators must propagate the model rule into every nested spawn.
  • A second vendor model only reviews. It runs read-only at high reasoning effort with findings staying advisory, the orchestrator triages each finding on the merits and owns the verdict, and an error from that model drops the review with the omission stated in the report.

What Gets Delegated

  • Bulky sources (meeting transcripts, long chat threads, big document reads) go to subagents that return distilled findings only.
  • Wide file sweeps, multi-file codebase reads, and exploratory database queries go to subagents too.
  • Some steps stay in the main thread (installs, type-check, lint, git commit and push, PR creation, and narrow row-level DB verification on exactly the rows a migration touches), where IDs and current values get eyeballed firsthand because a summarizer can garble a UUID.

One stretch of transcripts shows the scale: a 37-agent parallel review fan-out over a 7-PR stack, five transcript pulls at once to answer one meeting question, and one security sweep agent per PR of a program. The main thread stayed a list of distilled verdicts throughout.

The Brief Contract - Every Implementation Brief Contains

  1. Verified requirements: premises checked against repo and memory first, with intentional behaviors that must not change called out.
  2. Target paths: the worktree to work in and the seed files to start from.
  3. Memory-only constraints: domain gotchas the repo doesn't document, plus an instruction to read the applicable AGENTS.md files.
  4. Scope discipline: minimal diff, no files outside the scope, no refactors, no comment churn, no drive-by cleanups.
  5. Output shape: files edited in place, plus a report carrying the change summary, the files touched, and anything contradicting the brief.
  6. Closing line, verbatim: "If the repo contradicts this brief, stop and report instead of implementing."

Scale Rules

  • There is no artificial agent cap, so N independent units get N parallel subagents, all launched in a single message.
  • Recursion stops at depth 5, and coordinators state the current depth and budget in every nested prompt.
  • Per-item agents return small structured verdicts (item, finding, recommendation) that parents aggregate upward, and when coverage is bounded the agent states what it dropped.
  • Subagent prompts explicitly authorize liberal tool use, telling each agent to "enumerate widely, search multiple phrasings in parallel, only conclude after exhausting the obvious sources", and their tokens never touch the main thread.
  • Implementers stay alive across rounds, so review findings and CI failures go back to the same agent that already holds full context.

8 · Layer 3 - The Atomic-PR Pipeline

The workhorse is a single slash command (a markdown file in the repo's .claude/commands/) that takes one described change and runs it end-to-end, fully autonomously. The invocation is the authorization, so the pipeline never stops for approval between steps. Every PR in the July 2026 spike went through this. The nine steps below are sanitized to work on any repo:

  1. Context sweep (mandatory). Two parallel tracks run before any code. The codebase track sends explore agents over the change area, covering files, callers, adjacent patterns, and conventions docs. The communications track sends one subagent per knowledge source (docs wiki, chat, meeting transcripts) to hunt for earlier discussions, specs, and constraints that never reached the repo. Everything relevant lands in the implementation brief.
  2. Fresh worktree. Every change starts from git worktree add ../repo-<slug> -b <branch> origin/<target>, so it builds on the branch it targets (inferred from the files touched, with our CI enforcing a path->branch rule), stays isolated from the main working tree so many changes proceed in parallel, and splits into two PRs from one invocation when it spans two surfaces.
  3. Delegated implementation + nested bug bash. A fresh implementer agent gets the brief (contract in section 7). After its diff is complete, it must spawn its own adversarial reviewer scoped to that diff, fix every real finding, and repeat until a pass comes back clean. Only then does it report up, listing what the inner bash found and fixed. "Done" alone is not an acceptable report.
  4. Verify + recursive review loop. Two reviewers start in the background (the second vendor's advisory model and a fresh adversarial bug bash agent over the full diff) while type-check, formatter, and linter run. Every bash names security and privacy as a dimension (what does the frontend expose, what do DB access paths assume), with a lower bar for internal-only surfaces. The orchestrator triages findings on the merits, and fixes go back to the live implementer. The loop repeats with fresh reviews each round until a round produces zero findings worth fixing. Anything rendered also gets a visual pass in a real browser, in both light and dark themes, run from a throwaway server out of the PR worktree on a free port so agent verification never touches my foreground dev server.
  5. Diff slimming pass. After the loop converges, the orchestrator reads the final diff once more asking what can be removed at no cost, strips dead parameters, needless indirection, helpers with one consumer, and comment churn while changing no behavior, and applies the same minimization to tests at authoring time, where every test must name the distinct contract only it pins or be merged into another test or deleted.
  6. Commit, push, PR. The commit message is imperative with a short why plus a model attribution trailer, the PR body is a Summary and a Test plan with the actual run output, and the pipeline files the tracking ticket automatically, following the team's project conventions.
  7. Review bot triage. A background poll waits for the team's PR review bot, every comment gets an explicit judgment, applied (via the implementer) or skipped with a one-line reason, the pipeline replies on every bot thread with the verdict and commit SHA so human reviewers can see each finding was addressed, and a bot that never shows blocks nothing.
  8. Preview verification. Because our deploy pipeline can report success for a build it skipped, a green check alone proves nothing, so the step confirms that a live deployment exists and loads before the link goes into the report.
  9. Final report. The report carries the PR URL, a one-paragraph diff summary, the review triage verdicts, the preview link, and the worktree path, in the numbered format from section 6, and the worktree stays alive for iteration until merge.

Stacked programs add three rules. Branch each PR from its predecessor, so its GitHub diff shows only its own work from the moment it opens. Titles carry [PR n/N - Program] in merge order. Squash-merge breaks child branches. After each parent merge I run an explicit git rebase --onto to drop the parent's commits, because a plain rebase leaves them in. The transcripts surfaced two more traps. A stacked PR runs almost no checks, so a "clean" merge state can just mean "no checks configured". I retarget each PR and watch the full suite before every merge. A bot that doesn't auto-review stacked bases needs an explicit review request after every retarget.

The Seven Adversarial Layers

Human review and PR bots optimize for correctness on the diff. Neither routinely asks "who can call this, as which role, from where?", so that question gets its own agents. The layers fire at different points:

#LayerWhen it fires
1Pre-plan review themes checklist: recurring failure themes distilled from past heavily reviewed work (default privilege traps, audit atomicity, gates shipping with their keys, migrations as operations, contract drift)Design time, before implementation, on database work and multi-PR stacks
2Implementer's nested bug bash: the implementing agent spawns its own adversaryInside implementation, loops until an inner pass is clean
3Cross-vendor read-only review (a second vendor's model at high reasoning effort, advisory only)Verify stage, backgrounded, fresh pass every loop round
4Adversarial bug bash over the full combined diff, prompted to break the code. Findings must survive re-reading the actual code pathVerify stage, backgrounded, fresh pass every loop round
5Per-PR security sweep: one read-only agent per PR, in parallel, each given that PR's diff, the repo's permission model, and a demand for a concrete attack scenario per findingDB permission changes, visibility gates, new API routes, multi-PR stacks

Layer 5 earned its cost on one 7-PR stack. Before merge it caught 9 real security issues that a 27-comment human review and the PR bot both missed, among them a cross-site request path into production writes and an anonymously callable privileged DB function. Each agent builds a threat model specific to its own PR diff instead of running a generic checklist, and the demand for a concrete attack scenario filters out theoretical findings. Internal-only surfaces get a lower bar, so noise about insider visibility doesn't bury the real findings on routes that face the public and study participants.

9 · Layer 4 - Memory, Skills, and the Retro Loop

Persistent Memory

  • Memory is a per-project directory of markdown files, one fact per file (132 files today), with a one-line index that loads into every session, covering who I am, feedback on how to work (with the why attached), ongoing project state, and reference pointers.
  • The files hold corrections I've given, API gotchas discovered at 2am ("this provider returns a black image as HTTP 200 at 50 steps, cap at 49"), premises that turned out wrong, and environment traps, while anything the repo or git history already records stays out.
  • An agent that starts with those 132 facts spends none of my time re-learning them.

Skills

  • Repeated workflows get promoted into skill and command files, markdown playbooks the agent loads on demand, and the eight in use today cover the atomic-PR pipeline itself, transcript handling rules, and domain runbooks for generation runs, data exports, and ticket filing.
  • A skill also encodes pathologies: what the tools get wrong, which outputs can't be trusted, what to verify before believing a green status.

The Retro Loop - The System Improves Itself

  • When a workstream closes, a dedicated retro agent reads the full session transcripts (main thread and every subagent) and hunts for corrections I gave, premises that were wrong, workarounds discovered, steps a skill was missing, and repeated manual sequences worth codifying.
  • It returns concrete suggested edits (target file, proposed diff, transcript evidence) that I approve or reject before they land in CLAUDE.md, the skills, or memory, so the system never edits its own rules unreviewed.

10 · Replicate It - A Setup Guide

Nothing here needs my repo. The steps below are sorted by payoff, and each one works without the ones after it.

  1. Write the communication contract first. Create ~/.claude/CLAUDE.md in about 30 minutes, covering how you want answers formatted (steal the numbered hierarchy rule), the "answer questions before implementing" rule, and how you review (for example, "diffs on GitHub only"), because the file loads into every session and those ~50 lines pay for themselves in each one.
  2. Split orchestrator and implementer. Add a delegation section where the main loop verifies premises, writes briefs, and reviews while subagents (explicitly named model tier on every spawn) explore and implement, then copy the six-point brief contract from section 7 verbatim, especially the closing line about stopping when the repo contradicts the brief.
  3. Adopt worktree isolation. One change gets one worktree off the target branch, which is what makes 5+ parallel changes tractable and keeps your main tree clean for the next conversation.
  4. Build your atomic-PR command. Write a markdown file in your repo's .claude/commands/ that implements section 8's nine steps against your CI, review bots, and deploy pipeline, starting minimal (sweep -> worktree -> implement -> verify -> PR) and letting the retro loop grow it, the way mine grew to ~200 lines over a month of "that failure becomes a rule" edits, a third of them double-checking status signals that lie (section 11).
  5. Layer the review pressure. Add the layers in order of value: (a) the nested bug bash inside the implementer, (b) a fresh adversarial review agent over the final diff with security/privacy as a named dimension, (c) a second vendor model in read-only mode, which finds a different class of failure, and (d) whatever PR bot your team runs, with the rule to reply on every thread, recursing until a clean round.
  6. Start the memory habit. Write one indexed markdown file for every correction you type twice and one for every gotcha that cost you an hour, then add the retro agent (section 9) so the harvesting happens automatically at thread close.
  7. Only then scale parallelism. Thread letters, stacked PR conventions, and 10-agent fan-outs are the processing layer for a volume problem you won't have on day one, so they matter once you're running multiple workstreams concurrently.

Copy Verbatim vs Adapt vs Never Copy

  • Copy near verbatim (mechanism, portable): the pipeline stage structure, the two-track context sweep, worktree + target branch by path, the recursive dual reviewer loop with the named security dimension, the nested implementer bug bash, the stacked PR branching and rebase --onto mechanics, replying on every bot thread, and the numbered hierarchy + thread letter message format.
  • Adapt per person/team: the commit attribution trailer, your ticket tracker's conventions, which knowledge sources your context sweep covers, the cross-vendor reviewer model and flags (or drop that layer and run extra adversarial rounds on your own vendor's model), and the pre-plan review themes, which encode your repo's failure history and are worth regenerating from your own review record.
  • Never copy (machine specific): lint hook environment variables, env file symlink paths, scratchpad and publish directory conventions, and in general anything with an absolute path in it, which is a trap in someone else's config.

Whatever you copy, keep the split, with personal workflow living in personal config (user-global CLAUDE.md, gitignored command files) and the repo's shared agent docs staying free of it. Total setup from zero is about a weekend. The contract file, the orchestrator/implementer split, and the worktree habit (steps 1-3) carried about half of my speedup. The pipeline and the review stack made the engineering itself delegable.

11 · Costs and Failure Modes

The Costs

  • Token spend is real. Every PR burns an orchestrator, an implementer, and 2-4 review passes, and that spend sits in my infrastructure budget, smaller than the cost of the review hours I would otherwise burn on findable bugs.
  • Review bandwidth becomes the bottleneck. Reading 30 PRs a week is what the whole communication contract was written for, so fix the report format before the volume arrives.
  • Some work stays human. I delegate the typing and keep the accountability, so six things stay mine: premise verification, brief writing, every merge, every DB migration application, deprecations that need judgment, and the final read of every diff.

The Failure Modes

  • Agents execute flawed briefs without complaint. Because the review stack catches bad code while a wrong premise executed with full confidence passes straight through that stack, verifying premises before the brief goes out is the one step I never hand to an agent.
  • Green statuses lie. A third of my pipeline file is workarounds for signals that report success while meaning nothing (skipped builds reporting green, "clean" merge states meaning "no checks configured"), so every status you rely on needs a liveness probe the first time, and the probe belongs in the pipeline file.
  • The data carries confounds. The July jump coincides with both a stronger model and the workflow change (I can't cleanly separate them), April 2026 dips because I was on holiday, and "manual" in 2025 means "no attribution in git", so editor autocomplete and chat paste are invisible to this analysis.

Pitfalls the Transcripts Surfaced

  • Backgrounded CLI reviewers hang silently on stdin. One review burned 13 minutes waiting on "reading additional input from stdin", so close stdin (< /dev/null) when backgrounding anything that can prompt for input.
  • One dead import can poison a whole dev server. Under some bundlers a single unresolved module makes every route return that module's compile error, so an API route that 500s in ~0.1s means the build broke and the query never ran, with the corollary that a cleanup PR that greps for consumers and finds none can still break another branch, because that branch holds the only pages that import the removed code.
  • The same symptom does not mean the same cause. Re-measure before reusing a past remedy, because one session nearly re-applied an old fix to a different failure layer just from a matching error message.
  • Session transcripts persist to disk unredacted. Anything pasted into a session, credentials included, lands in plaintext, so never paste live secrets.
  • A silently waived step blinds the reviewer. When I waive a pipeline step (a context sweep skipped, a check deferred), I state the waiver and the reason, so the reviewer knows what protection I traded away.

   diff references only.
4. Surface diffs where I review (<GitHub PR view>). Uncommitted local
   edits are invisible. "Check the file" is never an acceptable handoff.
5. Reference files by full path. Never hand back a bare basename.

# Delegation
1. Division of labor: the main loop model orchestrates, verifies premises, and
   reviews. <implementer-tier> subagents explore and implement.
   <cross-vendor-model> gives a read-only second opinion.
2. Keep bulky raw material out of the main thread: transcripts, long chat
   threads, big document reads, wide file sweeps, exploratory DB queries all go
   to subagents that return distilled findings only.
   - Exception: narrow row level verification of exactly the rows a migration
     touches stays in the main thread - see the IDs firsthand.

## Model policy - STRICT
1. Every subagent spawn carries an explicit model param. Never
   inherit by omission - a spawn without the param is a rule violation even for
   "cheap" read-only searches.
2. Coordinators must pass this requirement into every nested spawn.

## Scale - no agent cap
1. Standing permission to spawn as many parallel subagents as there are
   independent units of work. One subagent per item at the lowest level. Do not
   iterate a long list serially, and state bounded coverage explicitly. Never
   sample silently.
2. Recurse to depth 5 at most - each level returns only distilled findings
   upward, and coordinators state current depth + budget in nested prompts.

## Implementation - subagents implement, the main loop reviews
1. Any non-trivial implementation (>~5 lines or >1 file) is delegated to a
   fresh implementer agent with edit access, working in the target worktree.
2. Every implementation brief includes: (a) verified requirements - premises
   checked against repo and memory FIRST, behaviors that must not change named.
   (b) target worktree + seed file paths. (c) constraints that live only in
   memory + "read the applicable AGENTS.md files". (d) scope discipline -
   minimal diff, no files outside the scope, no refactors, no comment churn.
   (e) output shape - edit in place, report = summary + files touched +
   anything contradicting the brief. (f) verbatim: "If the repo contradicts
   this brief, stop and report instead of implementing."
3. Keep the implementing agent alive. Fixup rounds go to the SAME agent.
4. Steps that stay in the main thread: installs/type-check/lint, git
   commit/push, PR creation, DB row verification, migration application.
5. Review is mandatory: delegated diffs get the same review a human PR would - premise
   check, scope check, deletion hygiene, style conformance - before commit.

## Cross-vendor reviewer - advisory only
1. Read-only, high reasoning effort, output = findings only (file:line, severity,
   concrete failure scenario). No implementation, no write access.
2. Advisory only: triage each finding on the merits and own the
   verdict. If it errors, proceed without it and say so.

## Retro at thread close - MANDATORY on every workstream close
1. Spawn one fresh retro subagent that reads the FULL session transcripts (main
   thread + every subagent) looking for: corrections given, premises that were
   wrong, workarounds discovered, steps a skill was missing, repeated manual
   sequences worth codifying.
2. Output = suggestions only (target file, concrete diff, transcript evidence).
   Apply only what the human approves.

# Atomic PR

1. Take the one atomic change in $ARGUMENTS. Scan its context, implement it in
   an isolated worktree, ship it as a PR against the correct target branch,
   triage the review bot, end with the preview link.
2. Work fully autonomously - the invocation is the authorization. Stop only when
   the WHAT of the change is ambiguous. HOW is never a reason to stop.

## Scope discipline
1. One coherent change set. No drive-by refactors.
2. Deletion hygiene, recursively: grep every removed import/prop/component for
   other consumers. If the removed code was the last consumer, delete upstream
   too, then recurse.

## Target selection
1. Pick the PR target by the files the change touches (<your path->branch
   rule, ideally enforced in CI>). A change spanning two surfaces splits into
   two PRs from this one invocation, dependency stated in both bodies.

## Pipeline
### 1. Context sweep (mandatory, parallel)
- Codebase track: explore agents over the change area - files, callers,
  adjacent patterns, applicable conventions docs.
- Comms track: one subagent per knowledge source (<wiki>, <chat>,
  <meeting-notes>) hunting earlier specs and constraints that never
  reached the repo. Distilled findings only - "no relevant context" is valid
  only after several phrasings per source.
- Every premise-bearing finding lands in the step-3 brief.

### 2. Worktree
    git fetch origin <target>
    git worktree add ../<repo>-<slug> -b <branch> origin/<target>
- A PR forks from the branch it targets. Main tree never dirtied.
- <your lint-hook / env-symlink specifics here>

### 3. Implement (delegated) + nested bug bash
- Fresh implementer agent + the brief contract (see CLAUDE.md).
- After its diff is complete, the implementer spawns its OWN adversarial
  bug bash subagent scoped to the diff, fixes every real finding, repeats
  until an inner pass is clean - only then reports up, listing what the inner
  bash found. "Done" alone is not an acceptable report.
- Test minimization at authoring time: every test must name the distinct
  contract only it pins, or it is merged/deleted.

### 4. Verify + recursive review loop
- Start BOTH reviewers in the background first (<cross-vendor read-only
  review> plus a fresh adversarial bug bash agent over the full diff, prompted
  to BREAK the code - findings only, file:line + severity + concrete failure
  scenario), then run verify while they work: type-check, formatter, linter
  (warning count diffed against the stashed base).
- Security & privacy is a NAMED dimension of every bash: what does the
  frontend expose, what do DB access paths assume, who can call this, as
  which role, from where. Calibrate lower for internal-only surfaces.
- Triage findings on the merits. Fixes go to the live implementer.
  Re-run BOTH reviewers fresh. Loop until a round yields zero findings worth
  fixing.
- UI pass when anything renders: real browser, light AND dark themes.

### 5. Diff slimming pass
- After the loop converges: subtraction only - dead params, needless
  indirection, helpers with one consumer, comment churn.

### 6. Commit, push, PR
- Imperative summary + short why + attribution trailer.
- PR body: Summary + Test plan with the actual run output.
- File the tracking ticket immediately when the PR opens (one issue per PR).

### 7. Review bot triage
- Poll in the background for the bot (author-triggered - a missing review can
  just mean "not enabled", so read it as unknown rather than clean). Explicit
  verdict per comment: apply if genuinely correct and in scope, else skip with
  a one-line reason.
- REPLY ON EVERY BOT THREAD on the PR itself (fixed -> what changed + SHA,
  skipped -> rationale with evidence).

### 8. Preview verification
- Confirm a live deployment exists and loads before reporting the link. A
  green deploy status alone proves nothing (skipped builds can report green).

### 9. Final report
- PR URL, a one-paragraph diff summary, triage verdicts, preview URL, worktree
  path (left in place for iteration until merge).

## Stacked PRs
1. Every PR's diff shows ONLY its own work from the moment it opens: branch
   each PR from its predecessor's branch, open with --base <predecessor>.
2. Titles: [PR n/N - Program] in MERGE order.
3. Squash-merge trap: children never auto-collapse. After each parent merge:
   git rebase --onto origin/<main> <old-parent-tip> <child>
   (a plain rebase leaves them in), force-with-lease, re-verify the diff collapses.
4. Stacked CI is a mirage: retarget and watch the FULL suite before merging.
