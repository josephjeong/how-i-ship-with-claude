How I ship ~9× faster with a multi-agent Claude workflow

I lead media-generation benchmarking at Artificial Analysis. Over 19 months I went from ~13 hand-written PRs a month to 115 agent-built PRs in July 2026 — with fewer reverts, not more. This page is the complete, honest picture: the measured acceleration, the workflow that produced it, and everything you need to replicate the setup. All numbers come from the git/GitHub history of one production monorepo (505 merged PRs, ~2,500 branch commits).

2 · Three eras of working

The velocity chart splits into three regimes, and the character of the work changes more than the count does.

2025 — manual (157 PRs, ~13/month)

  • Scripts and provider wiring. PR bodies barely existed — 64% were empty; 8 of 157 had hand-written prose.
  • Big-bang shapes: one PR landed +10k/−9.5k lines in 43 commits; another took 211 commits to ship a 111-line change.
  • Ship-then-discover: a feature merged and was reverted 3 days later; 5% of titles said "temp/hotfix/rollback".
  • The disposition predated the tooling — an Aug 2025 PR body, in full: "made with cursor agent + gpt-5. Would be curious how cooked it is ;D"

Jan–May 2026 — single-agent Claude Code (141 PRs, ~35/month excluding a holiday month)

  • The template era: 89% of PRs get a Summary + Test plan, applied uniformly to the point of ritual (a one-image logo PR got a full test plan).
  • Built the instruments: internal tooling jumped from 5% to 29% of PRs — dashboards and trackers I then lived in for the rest of the year.
  • Work shifted from repair to design: 2025's "temporary fix" PRs became engineered integrity features.
  • Ambition present, decomposition not yet: the era still produced 117-commit single-PR monsters.

Jun 2026+ — multi-agent orchestration (207 PRs, 115 in July alone)

  • The unit of work became the program, not the PR: 6-and-7-PR stacks with merge order encoded in the title ([PR n/N - Program Name]); half of all PR bodies reference another PR (2% → 9% → 50% across the eras).
  • Bodies argue with evidence, not checkboxes: unchecked - [ ] boxes fell from 80% of PRs to 20%, displaced by already-run results — type-check/lint/test output, and production EXPLAIN ANALYZE plans pasted into the body.
  • The review loop is visible in history: review-bot findings and cross-model review batches are named and answered in PR bodies; review-fix commits went 2 → 7 → 24 per era.
  • The multi-agent fingerprint: 23 PRs carry two Claude models as co-authors — the orchestrator and its implementing subagent — and every commit carries a session-transcript link (0 before June, 495 after).
  • The system builds its own tooling: ~8% of PRs ship runbooks, CLIs and agent skills for future agent runs — a category that didn't exist in earlier eras.

The session model

  • One long-lived session per vague context, not one per task. One session that week covered a whole program area for five days (591 messages); another covered a single evening's page fix. Workstreams are born inside the session as things come up, each getting a thread letter the moment it spawns.
  • Prompts are cheap; verification is not. Real openers from that week: plz fix thsi page - <internal url>, they should be the same number, lest do 1. Typos and vagueness are fine because the pipeline does the context reconstruction. What is never skipped is the proof demand at the end: wait can u show me it working in local — approval only after screenshots.
  • Sessions end by writing durable learnings to memory files, so the next session recalls instantly instead of re-discovering. A solved problem that never got a memory entry costs a full re-discovery round later — measured, that week, the hard way.

5 · The architecture

The system has four layers. None of them is exotic; the leverage comes from writing all four down so every session starts from the same contract instead of re-deriving it.

One frontier model (currently Claude Fable 5) runs the main loop and never writes non-trivial code. It verifies premises, writes briefs, spawns implementer subagents (currently Claude Opus tier) in isolated git worktrees, reviews their diffs like a human reviewer would, and owns every verdict. Independent review pressure comes from three directions: each implementer runs its own adversarial "bug bash" subagent before reporting; a second-vendor model (OpenAI's Codex CLI in read-only mode) reviews every diff advisorily; and the team's PR review bot comments on the open PR. The human — me — reviews on GitHub and owns the merge.

The principles under it

  1. Orchestrate, don't type. The main-loop model's context is precious. Bulk work — file sweeps, long threads, transcripts, implementation — happens in subagents that return distilled summaries. The orchestrator sees conclusions, not raw dumps.
  2. Premises are the safety boundary. Implementer agents execute flawed briefs without pushing back. So the orchestrator verifies every premise against the repo and memory before writing the brief, and every brief ends with: "If the repo contradicts this brief, stop and report instead of implementing."
  3. Review is structural, not optional. Nested bug bash → cross-model advisory review → recursive loop until a round produces zero findings worth fixing → PR bot triage with a reply on every thread. No diff reaches a PR having been read by only one mind.
  4. Parallelism has no artificial cap. N independent units of work get N subagents — one per file to migrate, model to probe, PR to triage. Coordinators recurse (bounded at depth 5), and each level returns only distilled findings upward.
  5. Everything learned gets written down. Corrections, gotchas, and workflow improvements land in persistent memory files or skill documents. A retro agent reads the full session transcripts at the end of each workstream and proposes edits to the system itself.

6 · Layer 1 — the CLAUDE.md contract

A global ~/.claude/CLAUDE.md loads into every session. Mine has two halves: a communication contract (how answers must be formatted so I can process dozens of agent reports a day) and the delegation policy (section 7). The communication half, distilled:

  • Number everything. Every substantive answer is a numbered hierarchy (1 → 1.1 → sub-bullets), one idea per point, so I can reference any finding by number ("apply 2.3, skip 2.4"). Sub-points are real nested list items, each carrying 1–2 full explanatory sentences.
  • Thread letters. I run one long-lived session per broad context and spawn workstreams as they come up. Each workstream gets a stable letter for the session, and every message opens by naming its thread — letter plus name, never a bare letter. A message spanning threads is split into sections. Without this, interleaved agent reports become unreadable.
  • Phases and PRs are numbered, never lettered — letters are reserved for threads. Stacked PRs are numbered in merge order, in the GitHub title itself: [PR 2/6 - Program Name] …. The PR list then reads as a merge plan without opening anything.
  • Binary verdicts; dig, don't hedge. Investigations end in a green/red call at the top, caveats underneath as notes. Ambiguity triggers more research rounds, never a yellow verdict. Deep work first, short answer on top.
  • Signal density. Cut length, never data: every number, path, and stated uncertainty survives editing; only the prose around them goes. Tables and code blocks over paragraphs carrying the same values.
  • Simplified-technical-English discipline for procedures and docs: one name for one thing, active voice, short common words, one instruction per sentence, conditions before commands.
  • Answer questions before implementing. A message phrased as a question gets a grounded answer and recommendation — implementation waits for an explicit go. A principle-shaped remark ("we should never X") may be thinking-out-loud, not a spec; the agent asks one short question before building enforcement logic. This single rule prevents most wasted work.
  • Chat references, not chat payloads. The plan/code file is canonical; chat gets diff-style references. Diffs are reviewed on GitHub, never as uncommitted local edits — "check the file" is not a handoff.

Why this matters more than it looks: at 30+ agent-built PRs a week, your reading bandwidth is the bottleneck. The contract exists so that every report, from every agent, lands in a shape you can triage in seconds.

7 · Layer 2 — the delegation policy

Division of labor

  • The orchestrator (frontier tier) never implements non-trivial changes. It verifies premises, writes briefs, reviews diffs, and owns verdicts. Direct implementation only for trivial edits (<~5 lines) where the delegation round-trip costs more than it saves, or after a delegated attempt failed review twice.
  • Implementers (strong-but-cheaper tier) do all exploration and code-writing, each in a fresh agent with edit access, working in an isolated git worktree.
  • Every spawn names its model explicitly. No inherit-by-omission — a spawn without a model parameter is a policy violation even for "cheap" read-only searches. Coordinators must propagate the rule into every nested spawn.
  • A second-vendor model reviews, never implements. Read-only, high reasoning effort, advisory — the orchestrator triages each finding on the merits and owns the verdict. If it errors, proceed without it and say so.

What gets delegated by default

  • Meeting transcripts, long chat threads, big document reads — anything bulky returns distilled findings only.
  • Wide file sweeps, multi-file codebase reads, exploratory database queries.
  • What never gets delegated: installs/type-check/lint, git commit and push, PR creation, and narrow row-level DB verification on exactly the rows a migration touches — IDs and current values get eyeballed firsthand, not via a summarizer's transcription.
  • Scale in practice, from one week's transcripts: a 37-agent parallel review fan-out over a 7-PR stack; five parallel transcript pulls to answer one meeting question; one security-sweep agent per PR of a program. The main thread stayed a list of distilled verdicts throughout.

The brief contract — every implementation brief contains

  1. Verified requirements — premises checked against repo and memory first, intentional must-not-change behaviors named.
  2. Target worktree and seed file paths.
  3. Constraints that live only in memory (domain gotchas the repo doesn't document), plus an instruction to read the applicable AGENTS.md files.
  4. Scope discipline: minimal diff, no out-of-scope files, no refactors, no comment churn, no drive-by cleanups.
  5. Output shape: edit files in place; final report = change summary + files touched + anything contradicting the brief.
  6. Verbatim: "If the repo contradicts this brief, stop and report instead of implementing."

Scale rules

  • No artificial agent cap: N independent units → N parallel subagents, launched in a single message.
  • Recursion bounded at depth 5; coordinators state current depth and budget in every nested prompt.
  • Per-item agents return small structured verdicts (item, finding, recommendation); parents aggregate upward. Bounded coverage is stated explicitly — never silent sampling.
  • Subagent prompts explicitly authorize liberal tool use: "enumerate widely, search multiple phrasings in parallel, only conclude after exhausting the obvious sources." Their tokens never touch the main thread.
  • Keep implementers alive: review findings and CI failures go back to the same agent (which holds full context) rather than a fresh one.

8 · Layer 3 — the atomic-PR pipeline

The workhorse. A single slash-command (a markdown file in the repo's .claude/commands/) that takes one described change and runs it end-to-end, fully autonomously: the invocation is the authorization, and it does not stop for approval between steps. Every PR in the July-2026 spike went through this. The nine steps, sanitized to be repo-agnostic:

  1. Context sweep (mandatory). Two parallel tracks before any code: codebase (explore agents over the change area — files, callers, adjacent patterns, conventions docs) and communications (one subagent per knowledge source — docs wiki, chat, meeting transcripts — hunting for earlier discussions, specs, and constraints that never reached the repo). Everything relevant lands in the implementation brief.
  2. Fresh worktree. git worktree add ../repo-<slug> -b <branch> origin/<target> — every change builds on the branch it targets, isolated from the main working tree, so many changes proceed in parallel. Target branch is inferred from the files touched (our CI enforces a path→branch rule); a change spanning two surfaces is split into two PRs from one invocation.
  3. Delegated implementation + nested bug bash. A fresh implementer agent gets the brief (contract in section 7). After its diff is complete it must spawn its own adversarial reviewer scoped to that diff, fix every real finding, and repeat until a pass comes back clean — only then report up, listing what the inner bash found and fixed. Never just "done."
  4. Verify + recursive review loop. Two reviewers start in the background — the second-vendor advisory review and a fresh adversarial bug-bash agent over the full diff — while type-check, formatter, and linter run. Security and privacy is a named dimension of every bash (what does the frontend expose, what do DB access paths assume), with the bar calibrated lower for internal-only surfaces. Findings are triaged on the merits, fixes go back to the still-alive implementer, and the loop repeats — fresh reviews each round — until a round produces zero findings worth fixing. Anything rendered also gets a visual pass in a real browser, light and dark themes.
  5. Diff-slimming pass. After the loop converges, the orchestrator reads the final diff once more with one question: what can be removed without meaningful impact? Dead parameters, needless indirection, single-consumer helpers, comment churn. Subtraction only, no behavior change. (Tests get the same treatment at authoring time: an absolute-minimization rule — every test must name the distinct contract only it pins, or it is deleted/merged.)
  6. Commit, push, PR. Imperative commit message with a short why + model attribution trailer. PR body = Summary + Test plan with actual ran-it output. The tracking ticket is filed automatically against the team's project conventions.
  7. Review-bot triage. Background-poll for the team's PR review bot; make an explicit judgement on every comment — apply it (via the implementer) or skip with a one-line reason — and reply on every bot thread with the verdict and commit SHA, so human reviewers can see each finding was addressed. Never block on a bot that doesn't show.
  8. Preview verification. Poll the deploy status, but never trust a green check alone — confirm a live deployment actually exists and loads before reporting the link (our deploy pipeline can report success for a skipped build; the pipeline knows the difference).
  9. Final report. PR URL, one-paragraph diff summary, review-triage verdicts, preview link, worktree path — in the numbered format from section 6. The worktree stays alive for iteration until merge.

Stacked programs add three rules: every PR's GitHub diff must show only its own work from the moment it opens (branch each PR from its predecessor); titles carry [PR n/N - Program] in merge order; and because squash-merge breaks child branches, each merge is followed by an explicit git rebase --onto dropping the parent's commits — never a plain rebase. Two traps the transcripts surfaced: stacked CI is a mirage (a stacked PR runs almost no checks, and a "clean" merge state can mean "no checks configured", not "validated" — retarget and watch the full suite before each merge), and a bot that doesn't auto-review stacked bases needs an explicit review request after every retarget.

The seven adversarial layers

Human review and PR bots optimize for correctness on the diff; none of them systematically asks "who can call this, as which role, from where?" — so that question gets its own dedicated agents. Seven mechanisms, each firing at a different point:

#LayerWhen it fires
1Pre-plan review-themes checklist — recurring failure themes distilled from past heavily-reviewed work (default-privilege traps, audit atomicity, gates shipping with their keys, migrations-as-operations, contract drift)Design time, before implementation, on DB-heavy or multi-PR work
2Implementer's nested bug bash — the implementing agent spawns its own adversaryInside implementation, loops until an inner pass is clean
3Cross-vendor read-only review (a second vendor's model at high reasoning effort, advisory never blocking)Verify stage, backgrounded, fresh pass every loop round
4Adversarial bug bash over the full combined diff — prompted to break the code; findings must survive re-reading the actual code pathVerify stage, backgrounded, fresh pass every loop round
5Per-PR security sweep — one read-only agent per PR, in parallel, each given that PR's diff, the repo's permission model, and a demand for a concrete attack scenario per findingDB-permission changes, visibility gates, new API routes, multi-PR stacks
6The team's PR review bot — every inline comment gets a verdict reply on the threadAfter PR open

Why layer 5 earns its cost: on one 7-PR stack it caught 9 real security issues before merge — including a cross-site request path into production writes and an anonymously-callable privileged DB function — that a 27-comment human review and the PR bot both missed. The per-PR scoping is the trick: each agent builds a threat model specific to its diff instead of running a generic checklist, and the concrete-attack-scenario requirement filters out theoretical findings. Calibration matters equally: internal-only surfaces get a deliberately lower bar so insider-visibility noise doesn't drown the real findings on public and participant-facing routes.

9 · Layer 4 — memory, skills, and the retro loop

Persistent memory

  • A per-project directory of markdown files, one fact per file, with a one-line index that loads into every session. Types: who I am, feedback on how to work (with the why attached), ongoing-project state, and reference pointers.
  • What goes in: corrections I've given, API gotchas discovered at 2am ("this provider returns a black image as HTTP 200 at 50 steps — cap at 49"), premises that turned out wrong, environment traps. What stays out: anything the repo or git history already records.
  • The payoff compounds: an agent that already knows the codebase's forty sharp edges doesn't re-discover them at your expense.

Skills

  • Repeated workflows get promoted into skill files (markdown playbooks the agent loads on demand): the atomic-PR pipeline itself, transcript-handling rules, domain runbooks for recurring ops (generation runs, data exports, ticket filing).
  • A skill encodes not just steps but pathologies: what the tools get wrong, which outputs can't be trusted, what to verify before believing a green status.

The retro loop — the system improves itself

  • When a workstream closes, a dedicated retro agent reads the full session transcripts — main thread and every subagent — hunting for: corrections I gave, premises that were wrong, workarounds discovered, steps a skill was missing, repeated manual sequences worth codifying.
  • It returns concrete suggested edits (target file, proposed diff, transcript evidence). I approve or reject each one; approved edits land in CLAUDE.md, the skills, or memory. Suggestions only — the system never edits its own rules unreviewed.
  • This is the compounding mechanism: every mistake becomes a rule, every rule makes the next hundred PRs slightly better.

10 · Replicate it: a setup guide

Nothing here needs my repo. The order below is the order that pays off fastest — each step works without the ones after it.

  1. Write the communication contract first (30 minutes, immediate payoff). Create ~/.claude/CLAUDE.md with: how you want answers formatted (steal the numbered-hierarchy rule), the "answer questions before implementing" rule, and how you review (e.g. "diffs on GitHub, never uncommitted local edits"). This file is loaded into every session; it is the highest-leverage 50 lines you'll write.
  2. Split orchestrator and implementer. Add a delegation section: the main loop verifies premises, writes briefs, and reviews; subagents (explicitly named model tier on every spawn) explore and implement. Copy the six-point brief contract from section 7 verbatim — especially the closing line about stopping when the repo contradicts the brief.
  3. Adopt worktree isolation. One change = one worktree off the target branch. This is what makes 5+ parallel changes tractable and keeps your main tree clean for the next conversation.
  4. Build your atomic-PR command. A markdown file in your repo's .claude/commands/ implementing section 8's nine steps against your CI, review bots, and deploy pipeline. Start minimal (sweep → worktree → implement → verify → PR) and let the retro loop grow it. Mine is ~200 lines and grew over a month of "that failure becomes a rule" edits — a third of it is verification steps for status signals that turned out to lie.
  5. Layer the review pressure. In order of value: (a) the nested bug bash inside the implementer; (b) a fresh adversarial review agent over the final diff, with security/privacy as a named dimension; (c) a second-vendor model in read-only mode — genuinely different failure tastes; (d) whatever PR bot your team runs, with the reply-on-every-thread rule. Recurse until a clean round.
  6. Start the memory habit. Every correction you type twice, every gotcha that cost you an hour — one markdown file each, indexed. Then add the retro agent (section 9) so the harvesting happens automatically at thread close.
  7. Only then scale parallelism. Thread letters, stacked-PR conventions, and 10-agent fan-outs matter once you're running multiple workstreams concurrently — they're the processing layer for a volume problem you won't have on day one.

What to copy verbatim vs adapt vs never copy

  • Copy near-verbatim (mechanism, portable): the pipeline stage structure; the two-track context sweep; worktree + target-branch-by-path; the recursive dual-reviewer loop with the named security dimension; the nested implementer bug bash; the stacked-PR branching and rebase --onto mechanics; reply-on-every-bot-thread; the numbered-hierarchy + thread-letter message format.
  • Adapt per person/team: the commit attribution trailer; your ticket tracker's conventions; which knowledge sources your context sweep covers; the cross-vendor reviewer model and flags (or drop that layer and run same-vendor adversarial rounds only); the pre-plan review themes — they encode your repo's failure history, so regenerate them from your own review record.
  • Machine-specific, never copy blindly: lint-hook environment variables, env-file symlink paths, scratchpad and publish directory conventions. Anything with an absolute path in it is a trap in someone else's config.
  • Keep the split: personal workflow lives in personal config (user-global CLAUDE.md, gitignored command files) — never in the repo's shared agent docs. Your conventions shouldn't become your team's obligations by default.

Total setup from zero: a weekend. The contract file and worktree habit alone (steps 1–3) captured maybe half of my speedup; the pipeline and review stack turned it from "faster typing" into "delegable engineering".

11 · Honest costs and failure modes

  • Token spend is real. Every PR burns orchestrator + implementer + 2–4 review passes. I treat model spend as an engineering-infrastructure line item, and it is priced like one. The trade is deliberate: tokens are cheaper than my review time being wasted on findable bugs.
  • Your review bandwidth becomes the bottleneck. The whole communication contract exists because 30 PRs/week of reading is the new constraint. If you don't fix the report format, you'll drown in exactly the way that made me write the thread-letter rule.
  • Agents execute flawed briefs without complaint. The dangerous failure isn't bad code — the review stack catches that — it's a confidently-executed wrong premise. Premise verification before briefing is the boundary; treat it as non-delegable.
  • Green statuses lie. A third of my pipeline file is workarounds for signals that report success while meaning nothing (skipped builds reporting green, "clean" merge states meaning "no checks configured"). Every status you rely on needs a liveness probe the first time, and the probe belongs in the pipeline file.
  • Confounds in the data. The July jump coincides with both a stronger model and the workflow change — I can't cleanly separate them. April 2026's dip is a holiday, not a signal. And "manual" in 2025 means "no attribution in git": editor autocomplete and chat-paste were invisible to this analysis.
  • What stayed human: premise verification, brief-writing, every merge, every DB migration application, judgment-heavy deprecations, and the final read of every diff. The system moves the typing, not the accountability.

Pitfalls a week of transcripts surfaced

  • Backgrounded CLI reviewers hang silently on stdin. One review burned 13 minutes waiting on "reading additional input from stdin". Close stdin (< /dev/null) when backgrounding anything interactive-capable.
  • One dead import can poison a whole dev server. Under some bundlers a single unresolved module makes every route return that compile error — a near-instant 500 from an API route is a compile error, not a query problem. Corollary: a cleanup PR that greps for consumers and finds none may break the branch whose pages exist only elsewhere.
  • Never kill the human's foreground dev server. Agent verification runs a throwaway server from the PR worktree on a free port and screenshots there.
  • Same symptom ≠ same cause. Re-measure before reusing a past remedy; one session nearly re-applied an old fix to a different failure layer because the error message matched.
  • Session transcripts persist to disk unredacted. Anything pasted into a session — including credentials — lands in plaintext. Never paste live secrets.
  • Deviations are announced, never silent. When a pipeline step gets waived (a context sweep skipped, a check deferred), the waiver is stated with its reason — so the reviewer knows what protection was traded away.

1. Answer questions before implementing. A message phrased as a question gets a
   grounded answer + recommendation; implement only on an explicit go.
2. A principle-shaped statement ("we should never X") without an explicit
   add/change/build may be thinking-out-loud. Ask one short question before
   building enforcement logic.
3. No config blocks in chat. The plan/code file is canonical; chat gets
   diff-style references only.
4. Surface diffs where I review (<GitHub PR view>), never as uncommitted
   local edits. "Check the file" is never an acceptable handoff.
5. Reference files by full path, never a bare basename.

# Delegation
1. Division of labor: the main-loop model orchestrates, verifies premises, and
   reviews. <implementer-tier> subagents explore and implement.
   <cross-vendor-model> gives a read-only second opinion.
2. Keep bulky raw material out of the main thread: transcripts, long chat
   threads, big document reads, wide file sweeps, exploratory DB queries all go
   to subagents that return distilled findings only.
   - Exception: narrow row-level verification of exactly the rows a migration
     touches stays in the main thread — see the IDs firsthand.

## Model policy — STRICT
1. Every subagent spawn carries an explicit model param. Never
   inherit-by-omission — a spawn without the param is a rule violation even for
   "cheap" read-only searches.
2. Coordinators must pass this requirement into every nested spawn.

## Scale — no agent cap
1. Standing permission to spawn as many parallel subagents as there are
   independent units of work. One subagent per item at the lowest level; never
   one agent iterating a long list serially; never silent sampling.
2. Recurse to depth 5 at most; each level returns only distilled findings
   upward, and coordinators state current depth + budget in nested prompts.

## Implementation — subagents implement, the main loop reviews
1. Any non-trivial implementation (>~5 lines or >1 file) is delegated to a
   fresh implementer agent with edit access, working in the target worktree.
2. Every implementation brief includes: (a) verified requirements — premises
   checked against repo and memory FIRST, must-not-change behaviors named;
   (b) target worktree + seed file paths; (c) constraints that live only in
   memory + "read the applicable AGENTS.md files"; (d) scope discipline —
   minimal diff, no out-of-scope files, no refactors, no comment churn;
   (e) output shape — edit in place; report = summary + files touched +
   anything contradicting the brief; (f) verbatim: "If the repo contradicts
   this brief, stop and report instead of implementing."
3. Keep the implementing agent alive. Fix-up rounds go to the SAME agent.
4. Main-thread-only steps: installs/type-check/lint, git commit/push, PR
   creation, DB row verification, migration application.
5. Review is mandatory: delegated diffs get a human-PR-grade review — premise
   check, scope check, deletion hygiene, style conformance — before commit.

## Cross-vendor reviewer — advisory only
1. Read-only, high reasoning effort, findings-only output (file:line, severity,
   concrete failure scenario). Never implementation, never write access.
2. Advisory, never blocking: triage each finding on the merits and own the
   verdict. If it errors, proceed without it and say so.

## Thread-close retro — MANDATORY on every workstream close
1. Spawn one fresh retro subagent that reads the FULL session transcripts (main
   thread + every subagent) looking for: corrections given, premises that were
   wrong, workarounds discovered, steps a skill was missing, repeated manual
   sequences worth codifying.
2. Output = suggestions only (target file, concrete diff, transcript evidence).
   Apply only what the human approves.

# Atomic PR

1. Take the one atomic change in $ARGUMENTS. Scan its context, implement it in
   an isolated worktree, ship it as a PR against the correct target branch,
   triage the review bot, end with the preview link.
2. Work fully autonomously — the invocation is the authorization. Stop only if
   ambiguous about WHAT to change (not HOW).

## Scope discipline
1. One coherent change-set. No drive-by refactors.
2. Deletion hygiene, recursively: grep every removed import/prop/component for
   other consumers; if the removed code was the last consumer, delete upstream
   too, then recurse.

## Target selection
1. Pick the PR target by the files the change touches (<your path→branch
   rule, ideally CI-enforced>). A change spanning two surfaces splits into
   two PRs from this one invocation, dependency stated in both bodies.

## Pipeline
### 1. Context sweep (mandatory, parallel)
- Codebase track: explore agents over the change area — files, callers,
  adjacent patterns, applicable conventions docs.
- Comms track: one subagent per knowledge source (<wiki>, <chat>,
  <meeting-notes>) hunting earlier specs and constraints that never
  reached the repo. Distilled findings only; "no relevant context" is valid
  only after several phrasings per source.
- Every premise-bearing finding lands in the step-3 brief.

### 2. Worktree
    git fetch origin <target>
    git worktree add ../<repo>-<slug> -b <branch> origin/<target>
- A PR forks from the branch it targets. Main tree never dirtied.
- <your lint-hook / env-symlink specifics here>

### 3. Implement (delegated) + nested bug bash
- Fresh implementer agent + the brief contract (see CLAUDE.md).
- After its diff is complete, the implementer spawns its OWN adversarial
  bug-bash subagent scoped to the diff, fixes every real finding, repeats
  until an inner pass is clean — only then reports up, listing what the inner
  bash found. "Done" alone is not an acceptable report.
- Test minimization at authoring time: every test must name the distinct
  contract only it pins, or it is merged/deleted.

### 4. Verify + recursive review loop
- Start BOTH reviewers in the background first (<cross-vendor read-only
  review>; a fresh adversarial bug-bash agent over the full diff, prompted
  to BREAK the code — findings only, file:line + severity + concrete failure
  scenario), then run verify while they work: type-check, formatter, linter
  (warning count diffed against the stashed base).
- Security & privacy is a NAMED dimension of every bash: what does the
  frontend expose; what do DB access paths assume; who can call this, as
  which role, from where. Calibrate lower for internal-only surfaces.
- Triage findings on the merits; fixes go to the still-alive implementer;
  re-run BOTH reviewers fresh. Loop until a round yields zero findings worth
  fixing.
- UI pass when anything renders: real browser, light AND dark themes.
- Final diff-slimming pass after the loop converges: subtraction only — dead
  params, needless indirection, single-consumer helpers, comment churn.

### 5. Commit, push, PR
- Imperative summary + short why + attribution trailer.
- PR body: Summary + Test plan with actual ran-it output.
- File the tracking ticket immediately at PR-open (one issue per PR).

### 6–7. Review-bot triage
- Background-poll for the bot (author-triggered — no review can mean "not
  enabled", not "clean"). Explicit verdict per comment: apply if genuinely
  correct and in scope, else skip with a one-line reason.
- REPLY ON EVERY BOT THREAD on the PR itself (fixed → what changed + SHA;
  skipped → evidence-backed rationale).

### 8. Preview verification
- Never trust a green deploy status alone — confirm a live deployment exists
  and loads before reporting the link (skipped builds can report green).

### 9. Final report
- PR URL, one-paragraph diff summary, triage verdicts, preview URL, worktree
  path (left in place for iteration until merge).

## Stacked PRs
1. Every PR's diff shows ONLY its own work from the moment it opens: branch
   each PR from its predecessor's branch, open with --base <predecessor>.
2. Titles: [PR n/N - Program] in MERGE order.
3. Squash-merge trap: children never auto-collapse. After each parent merge:
   git rebase --onto origin/<main> <old-parent-tip> <child>
   (never a plain rebase), force-with-lease, re-verify the diff collapses.
4. Stacked CI is a mirage: retarget and watch the FULL suite before merging.
