Public write-up

How I ship ~9x faster with a multi-agent Claude workflow

I lead media generation benchmarking at Artificial Analysis. Over 19 months I went from ~13 handwritten PRs a month to 115 PRs built by agents in July 2026. Defects fell at the same time. 2025 had 5 reverts and 3 hotfixes, and the agent era has had 1 revert, which was scheduled work. All numbers come from the git/GitHub history of one production monorepo (505 merged PRs, ~2,500 branch commits).

Written August 2026. Numbers current through Aug 7, 2026. Single self-contained file, no trackers, no external requests.

2 · Three Eras of Working

The velocity chart splits into three regimes, and the character of the work changes more than the count does.

2025 - Manual (157 PRs, ~13/month)

  • Scripts and provider wiring. PR bodies barely existed. 64% were empty, and only 8 of 157 had handwritten prose.
  • Big bang shapes: one PR landed +10k/-9.5k lines in 43 commits. Another took 211 commits to ship a 111-line change.
  • Ship first, discover later: one feature was merged and reverted 3 days later. 5% of titles said "temp/hotfix/rollback".
  • The disposition predated the tooling. An Aug 2025 PR body, in full: "made with cursor agent + gpt-5. Would be curious how cooked it is ;D"

Jan-May 2026 - Single-Agent Claude Code (141 PRs, ~35/month excluding a holiday month)

  • The template era: 89% of PRs get a Summary + Test plan, applied uniformly to the point of ritual (a PR adding one logo image got a full test plan).
  • Built the instruments: internal tooling jumped from 5% to 29% of PRs, and those dashboards and trackers are what I lived in for the rest of the year.
  • Work shifted from repair to design: 2025's "temporary fix" PRs became engineered integrity features.
  • Decomposition lagged behind the ambition: the era still produced monsters, among them a single PR of 117 commits.

Jun 2026+ - Multi-Agent Orchestration (207 PRs, 115 in July alone)

  • The unit of work grew from the PR to the program: stacks of 6 and 7 PRs with merge order encoded in the title ([PR n/N - Program Name]). Half of all PR bodies reference another PR (2% -> 9% -> 50% across the eras).
  • Bodies argue with evidence: unchecked - [ ] boxes fell from 80% of PRs to 20%, displaced by actual run output (type-check/lint/test results, plus production EXPLAIN ANALYZE plans pasted into the body).
  • The review loop is visible in history: review bot findings and cross-model review batches are named and answered in PR bodies. Review fix commits went 2 -> 7 -> 24 per era.
  • The multi-agent fingerprint: 23 PRs carry two Claude models as co-authors (the orchestrator and its implementing subagent). Every commit also carries a session transcript link (0 before June, 495 after).
  • The system builds its own tooling: ~8% of PRs ship runbooks, CLIs, and agent skills for future agent runs, a category that didn't exist in earlier eras.

The Session Model

  • One long-lived session per vague context, spanning many tasks. That week one session covered a whole program area for five days (591 messages), while another was a single evening's page fix. Workstreams are born inside the session as things come up, each getting a thread letter the moment it spawns.
  • Prompts are cheap. Verification is where the time goes. Real openers from that week: plz fix thsi page - <internal url>, they should be the same number, lest do 1. Typos and vagueness are fine because the pipeline does the context reconstruction. The proof demand at the end always stands: wait can u show me it working in local, with approval only after screenshots.
  • Sessions end by writing durable learnings to memory files, so the next session recalls them instantly instead of re-discovering them. A solved problem that never got a memory entry cost me a full re-discovery round that same week.

5 · The Architecture

The system has four layers. The leverage comes from writing all four down, so every session starts from the same contract instead of re-deriving it.

One frontier model (Claude Fable 5 today) runs the main loop and never writes non-trivial code. It verifies premises, writes briefs, spawns implementer subagents (currently Claude Opus tier) in isolated git worktrees, reviews their diffs like a human reviewer would, and owns every verdict. Independent review pressure comes from three directions: each implementer runs its own adversarial "bug bash" subagent before reporting, a second vendor model (OpenAI's Codex CLI in read-only mode) gives an advisory review of every diff, and the team's PR review bot comments on the open PR. The human (me) reviews on GitHub and owns the merge.

The Principles Under It

  1. Orchestrate and delegate the typing. The main loop model's context window is the scarce resource. Bulk work (file sweeps, long threads, transcripts, implementation) happens in subagents that return distilled summaries. The orchestrator sees only conclusions.
  2. Premises are the safety boundary. Implementer agents execute flawed briefs without pushing back, so the orchestrator verifies every premise against the repo and memory before writing the brief, and every brief ends with: "If the repo contradicts this brief, stop and report instead of implementing."
  3. Review is structural and mandatory. Nested bug bash -> cross-model advisory review -> recursive loop until a round produces zero findings worth fixing -> PR bot triage with a reply on every thread. At least two readers see every diff before it reaches a PR.
  4. Parallelism has no artificial cap. N independent units of work get N subagents: one per file to migrate, model to probe, PR to triage. Coordinators recurse (bounded at depth 5), and each level returns only distilled findings upward.
  5. Everything learned gets written down. Corrections, gotchas, and workflow improvements land in persistent memory files or skill documents. A retro agent reads the full session transcripts at the end of each workstream and proposes edits to the system itself.

6 · Layer 1 - The CLAUDE.md Contract

A global ~/.claude/CLAUDE.md loads into every session. Mine has two halves: a communication contract (how answers must be formatted so I can process dozens of agent reports a day) and the delegation policy (section 7). The communication half, distilled:

  • Number everything. Every substantive answer is a numbered hierarchy (1 -> 1.1 -> sub-bullets), one idea per point, so I can reference any finding by number ("apply 2.3, skip 2.4"). Sub-points are real nested list items, each carrying 1-2 full explanatory sentences.
  • Thread letters. I run one long-lived session per broad context and spawn workstreams as they come up. Each workstream gets a stable letter for the session, and every message opens by naming its thread, letter plus name. A message spanning threads is split into sections. Without this, interleaved agent reports become unreadable.
  • Phases and PRs are numbered. Letters are reserved for threads. Stacked PRs are numbered in merge order, in the GitHub title itself: [PR 2/6 - Program Name] .... The PR list then reads as a merge plan without opening anything.
  • Binary verdicts. Investigations end in a green/red call at the top, with caveats underneath as notes. Ambiguity triggers more research rounds instead of a yellow verdict. Deep work first, short answer on top.
  • Signal density. Every number, path, and stated uncertainty survives editing, and only the surrounding prose goes. Tables and code blocks over paragraphs carrying the same values.
  • Simplified Technical English discipline for procedures and docs: one name for one thing, active voice, short common words, one instruction per sentence, conditions before commands.
  • Answer questions before implementing. A message phrased as a question gets a grounded answer and recommendation, and implementation waits for an explicit go. A remark that sounds like a principle ("we should never X") may be me thinking out loud rather than a spec, so the agent asks one short question before building enforcement logic. An agent once turned an offhand remark of mine into a serving invariant, and the change had to be backed out. That is the failure this rule stops.
  • Chat references only. The plan/code file is canonical, and chat gets references to the diff. I review diffs on GitHub, and uncommitted local edits are invisible to me. "Check the file" is not a handoff.

At 30+ PRs a week from agents, my reading bandwidth is the ceiling. The contract is what makes an agent report triageable in seconds.

7 · Layer 2 - The Delegation Policy

Division of Labor

  • The orchestrator (frontier tier) never implements non-trivial changes. It verifies premises, writes briefs, reviews diffs, and owns verdicts. Direct implementation only for trivial edits (<~5 lines) where the delegation round-trip costs more than it saves, or after a delegated attempt failed review twice.
  • Implementers (strong but cheaper tier) do all exploration and code writing. Each one is a fresh agent with edit access, working in an isolated git worktree.
  • Every spawn names its model explicitly. Nothing inherits a model by omission. A spawn without a model parameter is a policy violation even for "cheap" read-only searches. Coordinators must propagate the rule into every nested spawn.
  • A second vendor model reviews only. It runs read-only at high reasoning effort, and its findings stay advisory. The orchestrator triages each one on the merits and owns the verdict. If it errors, proceed without it and say so.

Delegated by Default

  • Anything bulky (meeting transcripts, long chat threads, big document reads) returns distilled findings only.
  • Wide file sweeps, multi-file codebase reads, exploratory database queries.
  • Never delegated: installs/type-check/lint, git commit and push, PR creation, and narrow row-level DB verification on exactly the rows a migration touches. IDs and current values get eyeballed firsthand, because a summarizer can garble a UUID.
  • Scale in practice, from one week's transcripts: a 37-agent parallel review fan-out over a 7-PR stack, five transcript pulls at once to answer one meeting question, and one security sweep agent per PR of a program. The main thread stayed a list of distilled verdicts throughout.

The Brief Contract - Every Implementation Brief Contains

  1. Verified requirements: premises checked against repo and memory first, intentional behaviors that must not change called out.
  2. Target worktree and seed file paths.
  3. Constraints that live only in memory (domain gotchas the repo doesn't document), plus an instruction to read the applicable AGENTS.md files.
  4. Scope discipline: minimal diff, no files outside the scope, no refactors, no comment churn, no drive-by cleanups.
  5. Output shape: edit files in place, final report = change summary + files touched + anything contradicting the brief.
  6. Verbatim: "If the repo contradicts this brief, stop and report instead of implementing."

Scale Rules

  • No artificial agent cap: N independent units -> N parallel subagents, launched in a single message.
  • Recursion bounded at depth 5, and coordinators state current depth and budget in every nested prompt.
  • Per-item agents return small structured verdicts (item, finding, recommendation). Parents aggregate upward. When coverage is bounded, the agent states what it dropped.
  • Subagent prompts explicitly authorize liberal tool use: "enumerate widely, search multiple phrasings in parallel, only conclude after exhausting the obvious sources." Their tokens never touch the main thread.
  • Keep implementers alive: review findings and CI failures go back to the same agent (which holds full context) rather than a fresh one.

8 · Layer 3 - The Atomic-PR Pipeline

The workhorse is a single slash command (a markdown file in the repo's .claude/commands/) that takes one described change and runs it end-to-end, fully autonomously. The invocation is the authorization, so the pipeline never stops for approval between steps. Every PR in the July 2026 spike went through this. The nine steps, sanitized to work on any repo:

  1. Context sweep (mandatory). Two parallel tracks run before any code. The codebase track sends explore agents over the change area, covering files, callers, adjacent patterns, and conventions docs. The communications track sends one subagent per knowledge source (docs wiki, chat, meeting transcripts) to hunt for earlier discussions, specs, and constraints that never reached the repo. Everything relevant lands in the implementation brief.
  2. Fresh worktree. git worktree add ../repo-<slug> -b <branch> origin/<target>. Every change builds on the branch it targets, isolated from the main working tree, so many changes proceed in parallel. Target branch is inferred from the files touched (our CI enforces a path->branch rule). A change spanning two surfaces is split into two PRs from one invocation.
  3. Delegated implementation + nested bug bash. A fresh implementer agent gets the brief (contract in section 7). After its diff is complete, it must spawn its own adversarial reviewer scoped to that diff, fix every real finding, and repeat until a pass comes back clean. Only then does it report up, listing what the inner bash found and fixed. "Done" alone is not an acceptable report.
  4. Verify + recursive review loop. Two reviewers start in the background (the advisory review from the second vendor and a fresh adversarial bug bash agent over the full diff) while type-check, formatter, and linter run. Every bash names security and privacy as a dimension (what does the frontend expose, what do DB access paths assume), with the bar calibrated lower for internal-only surfaces. Findings are triaged on the merits, and fixes go back to the live implementer. The loop repeats with fresh reviews each round until a round produces zero findings worth fixing. Anything rendered also gets a visual pass in a real browser, in both light and dark themes.
  5. Diff slimming pass. After the loop converges, the orchestrator reads the final diff once more with one question: what can be removed at no cost? Dead parameters, needless indirection, helpers with one consumer, comment churn. Subtraction only, no behavior change. (Tests get the same treatment at authoring time under an absolute minimization rule. Every test must name the distinct contract only it pins. A test that cannot gets merged into another one or deleted.)
  6. Commit, push, PR. Imperative commit message with a short why + model attribution trailer. PR body = Summary + Test plan with the actual run output. The tracking ticket is filed automatically, following the team's project conventions.
  7. Review bot triage. Poll in the background for the team's PR review bot. Make an explicit judgment on every comment, apply it (via the implementer) or skip with a one-line reason, and reply on every bot thread with the verdict and commit SHA, so human reviewers can see each finding was addressed. Never block on a bot that doesn't show.
  8. Preview verification. Poll the deploy status. A green check alone proves nothing. Confirm that a live deployment actually exists and loads before reporting the link (our deploy pipeline can report success for a build it skipped, so probe the deployment itself).
  9. Final report. PR URL, a one-paragraph diff summary, review triage verdicts, preview link, and worktree path, in the numbered format from section 6. The worktree stays alive for iteration until merge.

Stacked programs add three rules. Every PR's GitHub diff must show only its own work from the moment it opens, so branch each PR from its predecessor. Titles carry [PR n/N - Program] in merge order. Because squash-merge breaks child branches, each merge is followed by an explicit git rebase --onto dropping the parent's commits. A plain rebase leaves them in. The transcripts surfaced two traps. Stacked CI is a mirage. A stacked PR runs almost no checks, and a "clean" merge state can just mean "no checks configured". Retarget and watch the full suite before each merge. A bot that doesn't auto-review stacked bases also needs an explicit review request after every retarget.

The Seven Adversarial Layers

Human review and PR bots optimize for correctness on the diff. The question "who can call this, as which role, from where?" gets its own agents. Seven mechanisms, each firing at a different point:

#LayerWhen it fires
1Pre-plan review themes checklist: recurring failure themes distilled from past heavily reviewed work (default privilege traps, audit atomicity, gates shipping with their keys, migrations as operations, contract drift)Design time, before implementation, on database work and multi-PR stacks
2Implementer's nested bug bash: the implementing agent spawns its own adversaryInside implementation, loops until an inner pass is clean
3Cross-vendor read-only review (a second vendor's model at high reasoning effort, advisory only)Verify stage, backgrounded, fresh pass every loop round
4Adversarial bug bash over the full combined diff, prompted to break the code. Findings must survive re-reading the actual code pathVerify stage, backgrounded, fresh pass every loop round
5Per-PR security sweep: one read-only agent per PR, in parallel, each given that PR's diff, the repo's permission model, and a demand for a concrete attack scenario per findingDB permission changes, visibility gates, new API routes, multi-PR stacks
6The team's PR review bot: every inline comment gets a verdict reply on the threadAfter PR open
7The orchestrator's own review at the bar of a human PR, plus the final diff slimming passBefore verify, and again after the loop converges

Layer 5 earned its cost on one 7-PR stack. Before merge it caught 9 real security issues that a 27-comment human review and the PR bot both missed, among them a cross-site request path into production writes and an anonymously callable privileged DB function. The per-PR scoping does the work. Each agent builds a threat model specific to its diff instead of running a generic checklist, and the demand for a concrete attack scenario filters out theoretical findings. Internal-only surfaces get a lower bar, so noise about insider visibility doesn't bury the real findings on routes that face the public and study participants.

9 · Layer 4 - Memory, Skills, and the Retro Loop

Persistent Memory

  • A per-project directory of markdown files, one fact per file (132 files today), with a one-line index that loads into every session. Types: who I am, feedback on how to work (with the why attached), ongoing project state, and reference pointers.
  • Goes in: corrections I've given, API gotchas discovered at 2am ("this provider returns a black image as HTTP 200 at 50 steps, cap at 49"), premises that turned out wrong, environment traps. Stays out: anything the repo or git history already records.
  • An agent that arrives already knowing those 132 facts re-discovers none of them at my expense.

Skills

  • Repeated workflows get promoted into skill and command files, markdown playbooks the agent loads on demand. The 8 in use today cover the atomic-PR pipeline itself, transcript handling rules, and domain runbooks for generation runs, data exports, and ticket filing.
  • A skill also encodes pathologies: what the tools get wrong, which outputs can't be trusted, what to verify before believing a green status.

The Retro Loop - The System Improves Itself

  • When a workstream closes, a dedicated retro agent reads the full session transcripts (main thread and every subagent) and hunts for corrections I gave, premises that were wrong, workarounds discovered, steps a skill was missing, and repeated manual sequences worth codifying.
  • It returns concrete suggested edits (target file, proposed diff, transcript evidence), and I approve or reject each one before it lands in CLAUDE.md, the skills, or memory. The retro agent only suggests, so the system never edits its own rules unreviewed.

10 · Replicate It - A Setup Guide

Nothing here needs my repo. The order below is the order that pays off fastest, and each step works without the ones after it.

  1. Write the communication contract first (30 minutes, immediate payoff). Create ~/.claude/CLAUDE.md. Cover how you want answers formatted (steal the numbered hierarchy rule), the "answer questions before implementing" rule, and how you review (e.g., "diffs on GitHub only"). The file loads into every session, and those ~50 lines pay for themselves in each one.
  2. Split orchestrator and implementer. Add a delegation section. The main loop verifies premises, writes briefs, and reviews. Subagents (explicitly named model tier on every spawn) explore and implement. Copy the six-point brief contract from section 7 verbatim, especially the closing line about stopping when the repo contradicts the brief.
  3. Adopt worktree isolation. One change = one worktree off the target branch. This is what makes 5+ parallel changes tractable and keeps your main tree clean for the next conversation.
  4. Build your atomic-PR command. A markdown file in your repo's .claude/commands/ implementing section 8's nine steps against your CI, review bots, and deploy pipeline. Start minimal (sweep -> worktree -> implement -> verify -> PR) and let the retro loop grow it. Mine is ~200 lines and grew over a month of "that failure becomes a rule" edits. A third of it is verification steps for status signals that lie (section 11).
  5. Layer the review pressure. In order of value: (a) the nested bug bash inside the implementer, (b) a fresh adversarial review agent over the final diff with security/privacy as a named dimension, (c) a second vendor model in read-only mode, which finds a different class of failure, and (d) whatever PR bot your team runs, with the rule to reply on every thread. Recurse until a clean round.
  6. Start the memory habit. Give every correction you type twice and every gotcha that cost you an hour one markdown file each, indexed. Then add the retro agent (section 9) so the harvesting happens automatically at thread close.
  7. Only then scale parallelism. Thread letters, stacked PR conventions, and 10-agent fan-outs matter once you're running multiple workstreams concurrently. They're the processing layer for a volume problem you won't have on day one.

Copy Verbatim vs Adapt vs Never Copy

  • Copy near verbatim (mechanism, portable): the pipeline stage structure, the two-track context sweep, worktree + target branch by path, the recursive dual reviewer loop with the named security dimension, the nested implementer bug bash, the stacked PR branching and rebase --onto mechanics, replying on every bot thread, and the numbered hierarchy + thread letter message format.
  • Adapt per person/team: the commit attribution trailer, your ticket tracker's conventions, which knowledge sources your context sweep covers, the cross-vendor reviewer model and flags (or drop that layer and run extra adversarial rounds on your own vendor's model), and the pre-plan review themes. The themes encode your repo's failure history, so regenerate them from your own review record.
  • Specific to one machine: lint hook environment variables, env file symlink paths, scratchpad and publish directory conventions. Anything with an absolute path in it is a trap in someone else's config.
  • Keep the split: personal workflow lives in personal config (user-global CLAUDE.md, gitignored command files). The repo's shared agent docs stay free of it.

Total setup from zero is about a weekend. The contract file and the worktree habit (steps 1 and 3) carried about half of my speedup. The pipeline and the review stack made the engineering itself delegable.

11 · Costs and Failure Modes

  • Token spend is real. Every PR burns an orchestrator, an implementer, and 2-4 review passes. It sits in the infrastructure budget. Tokens cost less than the review time I would waste on findable bugs.
  • Review bandwidth becomes the bottleneck. Reading 30 PRs a week is the constraint the whole communication contract was written for. Fix the report format before the volume arrives.
  • Agents execute flawed briefs without complaint. The review stack catches bad code. A wrong premise executed with full confidence passes straight through it. Verifying premises before the brief goes out is the one step I never hand to an agent.
  • Green statuses lie. A third of my pipeline file is workarounds for signals that report success while meaning nothing (skipped builds reporting green, "clean" merge states meaning "no checks configured"). Every status you rely on needs a liveness probe the first time, and the probe belongs in the pipeline file.
  • Confounds in the data. The July jump coincides with both a stronger model and the workflow change, and I can't cleanly separate them. April 2026's dip is a holiday month. "Manual" in 2025 means "no attribution in git". Editor autocomplete and chat paste were invisible to this analysis.
  • Still human: premise verification, brief writing, every merge, every DB migration application, deprecations that need judgment, and the final read of every diff. I delegate the typing and keep the accountability.

Pitfalls a Week of Transcripts Surfaced

  • Backgrounded CLI reviewers hang silently on stdin. One review burned 13 minutes waiting on "reading additional input from stdin". Close stdin (< /dev/null) when backgrounding anything that can prompt for input.
  • One dead import can poison a whole dev server. Under some bundlers a single unresolved module makes every route return that module's compile error, so an API route that 500s in ~0.1s means the build broke and the query never ran. Corollary: a cleanup PR that greps for consumers and finds none can still break another branch, because that branch holds the only pages that import the removed code.
  • Never kill the human's foreground dev server. Agent verification runs a throwaway server from the PR worktree on a free port and screenshots there.
  • Same symptom is not the same cause. Re-measure before reusing a past remedy. One session nearly re-applied an old fix to a different failure layer because the error message matched.
  • Session transcripts persist to disk unredacted. Anything pasted into a session, credentials included, lands in plaintext. Never paste live secrets.
  • Every deviation is announced. When a pipeline step gets waived (a context sweep skipped, a check deferred), the waiver is stated with its reason, so the reviewer knows what protection was traded away.

5. Reference files by full path.

# Delegation
1. Division of labor: the main loop model orchestrates, verifies premises, and
   reviews. <implementer-tier> subagents explore and implement.
   <cross-vendor-model> gives a read-only second opinion.
2. Keep bulky raw material out of the main thread: transcripts, long chat
   threads, big document reads, wide file sweeps, exploratory DB queries all go
   to subagents that return distilled findings only.
   - Exception: narrow row level verification of exactly the rows a migration
     touches stays in the main thread - see the IDs firsthand.

## Model policy - STRICT
1. Every subagent spawn carries an explicit model param. Never
   inherit by omission - a spawn without the param is a rule violation even for
   "cheap" read-only searches.
2. Coordinators must pass this requirement into every nested spawn.

## Scale - no agent cap
1. Standing permission to spawn as many parallel subagents as there are
   independent units of work. One subagent per item at the lowest level. Do not
   iterate a long list serially, and state bounded coverage explicitly.
2. Recurse to depth 5 at most - each level returns only distilled findings
   upward, and coordinators state current depth + budget in nested prompts.

## Implementation - subagents implement, the main loop reviews
1. Any non-trivial implementation (>~5 lines or >1 file) is delegated to a
   fresh implementer agent with edit access, working in the target worktree.
2. Every implementation brief includes: (a) verified requirements - premises
   checked against repo and memory FIRST, behaviors that must not change named.
   (b) target worktree + seed file paths. (c) constraints that live only in
   memory + "read the applicable AGENTS.md files". (d) scope discipline -
   minimal diff, no files outside the scope, no refactors, no comment churn.
   (e) output shape - edit in place, report = summary + files touched +
   anything contradicting the brief. (f) verbatim: "If the repo contradicts
   this brief, stop and report instead of implementing."
3. Keep the implementing agent alive. Fixup rounds go to the SAME agent.
4. Steps that stay in the main thread: installs/type-check/lint, git commit/push, PR
   creation, DB row verification, migration application.
5. Review is mandatory: delegated diffs get the same review a human PR would - premise
   check, scope check, deletion hygiene, style conformance - before commit.

## Cross-vendor reviewer - advisory only
1. Read-only, high reasoning effort, output = findings only (file:line, severity,
   concrete failure scenario). No implementation, no write access.
2. Advisory only: triage each finding on the merits and own the
   verdict. If it errors, proceed without it and say so.

## Retro at thread close - MANDATORY on every workstream close
1. Spawn one fresh retro subagent that reads the FULL session transcripts (main
   thread + every subagent) looking for: corrections given, premises that were
   wrong, workarounds discovered, steps a skill was missing, repeated manual
   sequences worth codifying.
2. Output = suggestions only (target file, concrete diff, transcript evidence).
   Apply only what the human approves.

# Atomic PR

1. Take the one atomic change in $ARGUMENTS. Scan its context, implement it in
   an isolated worktree, ship it as a PR against the correct target branch,
   triage the review bot, end with the preview link.
2. Work fully autonomously - the invocation is the authorization. Stop only if
   ambiguous about WHAT to change. HOW is never a reason to stop.

## Scope discipline
1. One coherent change set. No drive-by refactors.
2. Deletion hygiene, recursively: grep every removed import/prop/component for
   other consumers. If the removed code was the last consumer, delete upstream
   too, then recurse.

## Target selection
1. Pick the PR target by the files the change touches (<your path->branch
   rule, ideally enforced in CI>). A change spanning two surfaces splits into
   two PRs from this one invocation, dependency stated in both bodies.

## Pipeline
### 1. Context sweep (mandatory, parallel)
- Codebase track: explore agents over the change area - files, callers,
  adjacent patterns, applicable conventions docs.
- Comms track: one subagent per knowledge source (<wiki>, <chat>,
  <meeting-notes>) hunting earlier specs and constraints that never
  reached the repo. Distilled findings only - "no relevant context" is valid
  only after several phrasings per source.
- Every premise-bearing finding lands in the step-3 brief.

### 2. Worktree
    git fetch origin <target>
    git worktree add ../<repo>-<slug> -b <branch> origin/<target>
- A PR forks from the branch it targets. Main tree never dirtied.
- <your lint-hook / env-symlink specifics here>

### 3. Implement (delegated) + nested bug bash
- Fresh implementer agent + the brief contract (see CLAUDE.md).
- After its diff is complete, the implementer spawns its OWN adversarial
  bug bash subagent scoped to the diff, fixes every real finding, repeats
  until an inner pass is clean - only then reports up, listing what the inner
  bash found. "Done" alone is not an acceptable report.
- Test minimization at authoring time: every test must name the distinct
  contract only it pins, or it is merged/deleted.

### 4. Verify + recursive review loop
- Start BOTH reviewers in the background first (<cross-vendor read-only
  review> plus a fresh adversarial bug bash agent over the full diff, prompted
  to BREAK the code - findings only, file:line + severity + concrete failure
  scenario), then run verify while they work: type-check, formatter, linter
  (warning count diffed against the stashed base).
- Security & privacy is a NAMED dimension of every bash: what does the
  frontend expose, what do DB access paths assume, who can call this, as
  which role, from where. Calibrate lower for internal-only surfaces.
- Triage findings on the merits. Fixes go to the live implementer.
  Re-run BOTH reviewers fresh. Loop until a round yields zero findings worth
  fixing.
- UI pass when anything renders: real browser, light AND dark themes.

### 5. Diff slimming pass
- After the loop converges: subtraction only - dead params, needless
  indirection, helpers with one consumer, comment churn.

### 6. Commit, push, PR
- Imperative summary + short why + attribution trailer.
- PR body: Summary + Test plan with the actual run output.
- File the tracking ticket immediately when the PR opens (one issue per PR).

### 7. Review bot triage
- Poll in the background for the bot (author-triggered - a missing review can just
  mean "not enabled", so read it as unknown rather than clean). Explicit verdict per comment: apply if genuinely
  correct and in scope, else skip with a one-line reason.
- REPLY ON EVERY BOT THREAD on the PR itself (fixed -> what changed + SHA,
  skipped -> rationale with evidence).

### 8. Preview verification
- Never trust a green deploy status alone - confirm a live deployment exists
  and loads before reporting the link (skipped builds can report green).

### 9. Final report
- PR URL, a one-paragraph diff summary, triage verdicts, preview URL, worktree
  path (left in place for iteration until merge).

## Stacked PRs
1. Every PR's diff shows ONLY its own work from the moment it opens: branch
   each PR from its predecessor's branch, open with --base <predecessor>.
2. Titles: [PR n/N - Program] in MERGE order.
3. Squash-merge trap: children never auto-collapse. After each parent merge:
   git rebase --onto origin/<main> <old-parent-tip> <child>
   (never a plain rebase), force-with-lease, re-verify the diff collapses.
4. Stacked CI is a mirage: retarget and watch the FULL suite before merging.
